# P1：可解释组织、同步与外部上下文

## 四层信息契约

Orbit 不把不同可信度的信息混成一段结论。时间线详情固定区分：

1. **原始事实**：应用、窗口标题、起止时间及输入/空闲状态等本地记录。
2. **派生统计**：由事实确定性计算的时长、占比、切换次数等；不引入语义判断。
3. **分类推断**：分类、来源、理由、模型版本与置信度。来源可以是人工、规则、行为、AI、空闲或待分类。
4. **建议**：基于前三层生成的可选行动，不反向修改事实。

人工修正分类时，Orbit 先显示精确的 `应用 + 标题` 匹配预览、历史匹配数量和影响范围。用户可以只修正当前片段，也可以明确确认后创建仅作用于未来匹配的规则。预览本身不写数据库。

## 只追加事件同步

每个安装生成随机且持久化的 `deviceId`。每条事件带有设备内单调序号、发生时间、实体类型、实体 ID、操作、规范化 JSON 载荷及 SHA-256 完整性哈希；`eventId` 由这些字段确定性生成。数据库中的同步事件只追加，不原地改写。

合并先校验事件和载荷哈希，再按 `(occurredAt, deviceId, sequence, eventId)` 排序并做集合并。相同实体的投影使用同一排序键选择最后事件，因此导入顺序不影响结果。当前可跨设备投影的组织实体是人工保存的项目和任务（含任务状态）；人工分类修正作为审计事件保留，但不会尝试把一台设备的原始活动片段映射到另一台设备。

从旧版本升级后首次导出时，Orbit 会为尚无同步事件的既有项目与任务补一份基线事件；已建立基线的实体不会在后续导出中重复生成事件。

设置页可导出/导入同步包：

- 口令为空：可审计的 JSON 信封。
- 提供口令：PBKDF2-HMAC-SHA256（120,000 次）派生 AES-256-GCM 密钥；盐和 nonce 每次随机生成，口令不保存。
- 错误口令、篡改、事件 ID/序号冲突或无效载荷会拒绝导入。

同步包不包含应用时间线、窗口标题、网页内容、浏览器数据库路径或日历文件路径。当前传输方式是用户明确操作的文件导入/导出；云存储传输不在 P1 范围内。

## 日历与项目上下文

设置页支持导入：

- `.ics`：读取 `VEVENT` 的 UID、标题、开始/结束和状态。
- provider-neutral 项目 JSON：用于 Linear、Jira、GitHub Projects 等系统先导出/转换后本地导入。

项目 JSON 格式：

```json
{
  "sourceId": "linear-export",
  "sourceName": "Linear",
  "projects": [
    {
      "id": "project-1",
      "name": "Orbit",
      "status": "active",
      "tasks": [
        { "id": "task-1", "title": "Finish P1", "status": "started" }
      ]
    }
  ]
}
```

同一 `sourceId` 再次导入会更新快照并移除该来源已消失的项目/任务。今日页把这些条目标记为“仅本地 · 不作为活动事实”；日历事件只在与所选本地日重叠时显示，项目和任务作为组织上下文显示。它们不会增加监测时长，也不会静默上传原始活动。

日历时间支持 UTC（`...Z`）、浮动本地时间和全天日期。当前不带 IANA 时区数据库，因此遇到 `TZID=...` 会拒绝导入并提示改为 UTC 导出，避免把非本机时区静默解释成错误时间。

## 验证边界

- Rust 单元测试覆盖事件完整性、确定性集合并、加密往返、错误口令、ICS/JSON 解析。
- SQLite 集成测试覆盖迁移幂等性、事件重复导入、设备序号冲突、项目/任务确定性投影，以及来源快照刷新。
- 前端测试覆盖 IPC 参数、空返回兼容、四层解释和上下文的隐私标签。
